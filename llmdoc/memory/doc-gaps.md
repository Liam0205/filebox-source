# 未解决的问题

下面每条都写了现象和现状，以及可能的补法（都还没实施）。

## 登录限流只按 IP 计数

- 现状：免费计划的速率限制规则只能按 IP 计数，换着 IP 爆破拦不住，现在的防线是长口令。
- 补法：按用户名计数需要强一致的计数器。KV 不行（最终一致，而且每次失败都要写，会耗光写额度）；Durable Object 可以，但要先确认它在免费计划下超额是报错还是计费。

## release 满了时返回什么没有实测

- 现状：代码把上传返回的 422 当作 release 满了（见 `reference/platform-limits.md`）。定时任务会把数量控制在 950 以内，这条路径正常碰不到。
- 补法：在一个测试 release 里传满 1000 个小文件，看 GitHub 实际返回什么，再删掉这个 release。GitHub 对创建内容有频率限制，要分几个小时传。

## 上传和写索引之间失败会留下孤儿资产

- 现状：资产已经上传到 GitHub，但 `putFile` 失败（KV 写额度耗尽、网络错误）。这个资产没有索引，通过 filebox 的接口既看不到也删不掉，只能去 GitHub 上手工删。
- 孤儿资产不在 KV 里，自动清理既不计数也不删除，它们会一直占着 release 的名额。
- 补法：加一个管理员用的「对账」接口，列出 release 里所有 `fb_` 资产，与 KV 索引比对后删掉孤儿。资产的 label 里存着原始路径，可以据此恢复索引而不是直接删。

## 删除不能立即全网生效

- 现状：不带版本号的下载地址设置了 7 天的浏览器缓存，删掉文件后，已经缓存的浏览器仍能读到旧内容。Worker 侧会先查 KV，所以新请求会立即 404。
- 补法：缩短 `ASSET_TTL`，或者管理页只分享带 `?v=` 的地址。

## 文件列表一次拉全量

- 现状：`/api/files` 每次返回用户的全部文件，前端再按目录过滤。文件一多，响应会变大，KV 读和 list 的消耗也会跟着涨。
- 补法：按目录前缀 list（键空间已经支持，前缀是 `file:<用户>:<目录编码>%2F`），但这样只能列出直接子文件，子目录还得另外推导。
